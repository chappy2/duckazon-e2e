Historie bewusst auf dieses Ökosystem begrenzen: Container gab es schon vorher. 2019 startet die VS-Code-Preview, 2021 wird Codespaces für Team und Enterprise allgemein verfügbar, 2022 folgen offene Spezifikation und CLI. Heute gibt es Unterstützung lokal und bei Cloud-Anbietern: Codespaces betreibt den Dev Container auf einer VM; Ona nutzt Dev-Container-Konfigurationen auch für isolierte Agent-Umgebungen. Das zeigt die Breite des Ökosystems, keine gemessene Marktverbreitung. Auch IntelliJ IDEA unterstützt Dev Containers; CodeSandbox hat die Unterstützung im Oktober 2023 angekündigt. CodeSandbox verwendet außerdem eigene Projektdateien im Ordner .codesandbox, etwa tasks.json für Start- und Setup-Befehle. Das ist von der standardisierten .devcontainer/devcontainer.json zu unterscheiden. Die Anbieter können unterschiedliche Teile der Spezifikation unterstützen. 1:50–2:40. Den Bildweg von links nach rechts erklären: Playwright startet Chromium im Container mit --headed. DISPLAY ist hier :1 und verweist auf die virtuelle X-Anzeige; Fluxbox verwaltet die Fenster. TigerVNC stellt den Desktop über das VNC-Protokoll bereit. websockify überbrückt TCP zum VNC-Server und WebSocket zum Browser. VS Code leitet Port 6080 lokal weiter. Die dort geladene noVNC-Webanwendung zeichnet die Bildänderungen im Canvas. Maus- und Tastaturereignisse gehen in Gegenrichtung zum Desktop zurück. desktop-lite richtet diese Komponenten ein und startet sie automatisch. Der interne VNC-Port ist standardmäßig 5901; für diesen Browserzugang genügt die Weiterleitung von 6080. Port 5173 liefert dagegen die Shop-Webseite. Der lokale noVNC-Tab zeigt den entfernten Desktop; der eigentliche Testbrowser läuft im Container. Playwrights Automatisierung und der VS-Code-Debugger haben eigene Verbindungen und laufen nicht über VNC. Jetzt kurz zum vorbereiteten noVNC-Tab wechseln und den Desktop bedienen. Ein Browserfenster erscheint nach dem Start eines headed Tests.
